# Machining Assistant

Python implementations of CNN1D-VAE and LSTM-VAE for machining signal analysis, including classification of existing five-second WAV files, reconstruction, and experimental MSM classification.

## Add raw recordings, then prepare five-second samples

Keep each new recording in its own direct subfolder of `Dataset/Data/`, using the same layout as the existing recordings:

```text
Dataset/Data/<recording-id>/audio_000000.wav
Dataset/Data/<recording-id>/metadata.json
Dataset/Data/<recording-id>/events.json       (when supplied)
Dataset/Data/<recording-id>/playback.json     (when supplied)
```

Keep the supplied source metadata when copying clips. `SourceRecording.Folder` identifies clips from the same original recording. The current input contract is 44.1 kHz, stereo PCM16, one `audio_000000.wav` per recording folder. Other WAV names, multiple WAVs in one recording, nested batches, missing metadata, or incompatible formats produce an explicit error instead of silently omitting data.

Run this standalone preprocessing entry using the existing source split table:

```bash
python Dataset/Preprocessing/prepare_dataset.py
```

The preprocessor discovers new recordings, preserves the recording/source assignments in `Dataset/Preprocessing/dataset_splits.csv`, exports full five-second base WAVs, generates the currently selected artificial four classes, and writes the sample indexes. Unseen source groups go to training by default. A new clip from an existing validation/test source inherits that source's split. Short tails remain separate. Generated directories and previous exports are not scanned as new raw recordings.

The output is always **`Dataset/Processed_5s/samples.csv`**. Its `split` column selects train/validation/test, so only one CSV argument is needed:

```bash
python main.py --mode train --task classification --model lstm --csv Dataset/Processed_5s/samples.csv --epochs 20
```

`Dataset/Data/` holds the original recordings and annotations. The generated WAVs, CSVs, recipe and source snapshots live together in the separate `Dataset/Processed_5s/` directory. Every preparation builds and validates a temporary result, then replaces this fixed generated directory and updates `Dataset/Preprocessing/current_dataset.json`. Raw inputs and existing model weights are unchanged. The previous generated result is replaced, so copy it elsewhere first if you need to retain it for an experiment.

To inspect discovery/counts without writing files:

```bash
python Dataset/Preprocessing/prepare_dataset.py --dry-run
```

Normal preprocessing output shows only the resulting `samples.csv` path. Add `--verbose` to display per-recording progress and the full summary.

This entry follows the current **synthetic four-class** convention: originals are assigned `good`, with `sufficient/bad/very_bad` generated by sine injection. It does not infer those classes from event quality scores. Existing manual CSV target edits within these four classes are preserved for unchanged base PCM; conflicting edits or a different class definition require review rather than a silent reset. Real-label preparation is a separate future workflow; the model's configurable class count remains supported.

Generation refits its amplitude reference on the training bases only. Added data or a changed recipe can therefore change synthetic validation/test waveforms even when source assignments stay the same. Checkpoints save the data identity used for training. Full resume and historical test verification reject changed inputs; start a new training run for a changed prepared dataset. Rebuilding does not delete the old weights or make them compatible with new data automatically.

## Train the existing five-second WAV dataset

Use `--task classification --csv Dataset/Processed_5s/samples.csv` after preprocessing. One CSV row identifies **one complete five-second WAV and its class label**; its `split` column supplies train, validation or test. The current 31 raw recordings produce 1,180 training, 140 validation and 156 test samples, with four balanced classes: `good`, `sufficient`, `bad`, and `very_bad`. Each preparation reports its actual counts.

**Manual class configuration:** the generated dataset's `labels.json` is the source of class names and output count. The default generated mapping is:

```json
{"0": "good", "1": "sufficient", "2": "bad", "3": "very_bad"}
```

For a future dataset, use its own `labels.json` with consecutive IDs starting at 0 and unique names (at least two classes). The model automatically sets its output size to the number of entries. Keep each CSV row's `label` and `label_index` consistent with that mapping. The current CSV labels are the training targets; original generation labels in `samples.json` remain provenance metadata. Editing the class list does not relabel WAVs or generate new examples. A different class definition requires a fresh training run; a checkpoint preserves its original names/order and cannot resume under another mapping. `--task fourclass` remains an alias for `--task classification`.

Start training manually from the project root:

```bash
python main.py --mode train --task classification --model cnn --csv Dataset/Processed_5s/samples.csv --epochs 200
python main.py --mode train --task classification --model lstm --csv Dataset/Processed_5s/samples.csv --epochs 200
```

To run both models on the same combined CSV:

```bash
python main.py --mode train --task classification --model both --csv Dataset/Processed_5s/samples.csv --epochs 20
```

The CSV's parent directory supplies `labels.json` and the relative WAV-path base unless `--data-dir` is explicitly set. This mode reads only that combined CSV, not the three companion split CSVs. The selected absolute CSV path is saved in the checkpoint and reused by resume and independent test verification. A file containing only training rows is insufficient: the combined CSV must include all three active splits. Existing commands without `--csv` retain their prior behavior.

Choose one command, or use `--model both` to train CNN followed by LSTM. In PyCharm, select `main.py` and enter `--mode train --task classification --model cnn --csv Dataset/Processed_5s/samples.csv --epochs 200` in Parameters. No arguments displays help. `--task classification` is required; the older default task remains reconstruction.

The flow is `CSV path + label -> existing WAV -> Dataset/Preprocessing/fourclass_data.py -> CNN/LSTM -> configured class scores`. The preprocessing module reads the full stereo waveform as `[sound, vibration]` (channel 0 and channel 1), normalizes each channel with statistics fitted only on the training WAVs, and converts both channels to a tensor. It preserves all 220,500 original frames at 44.1 kHz. CNN receives 44 additional zero frames to meet its existing convolution shape requirement; reconstruction loss ignores those frames. LSTM receives exactly 220,500 frames. There is no new segmentation, frequency-feature conversion, channel discard, or per-file normalization. Original files remain unchanged.

The default batch size is 1. The training objective combines classification cross-entropy, waveform reconstruction MSE (weight 0.05), and KL loss (weight 0.001). Use `--epochs 1` for a manual first run before choosing a longer run; any observed metrics still need to be interpreted on this artificial-label task.

### LSTM on CPU: full five-second input, shorter recurrent sequence

Fresh LSTM classification runs group **441 consecutive stereo sample frames** (10 ms) into one recurrent input vector. The full input `(batch, 220500, 2)` becomes `(batch, 500, 882)` inside the encoder. Every raw sample value is retained, in time/channel order; no averaging, resampling, or spectral transform is applied. The decoder also runs 500 recurrent steps and restores a `(batch, 220500, 2)` waveform for the reconstruction loss.

The grouping and inverse grouping helpers live in `Dataset/Preprocessing/waveform_frames.py`. Normalization remains the shared training-only channel normalization. The external WAV/PCM interface, CSV assignments, class configuration, and five-second streaming output cadence stay the same. The CPU measurements below describe the earlier optimization checks; current training and inference select CUDA or CPU through `--device`.

```bash
python main.py --mode train --task classification --model lstm --csv Dataset/Processed_5s/samples.csv --lstm-frame-size 441 --epochs 20
```

`--lstm-frame-size` defaults to 441 for a fresh LSTM classification run and is saved as `model_config.frame_size`. Setting it to 1 selects the original per-sample recurrent layout. CNN ignores this LSTM-specific option. Existing checkpoints without the field use `frame_size=1`; a full resume preserves the checkpoint's architecture. Changing frame size alters learned layer dimensions and requires a fresh run, rather than resuming the old weights as if the models were identical. Old reconstruction and MSM checkpoints retain their default frame size of 1.

This changes the architecture, so faster execution alone does not establish equal or better classification quality. Formal training is started manually; the implementation checks use small fixtures and bounded CPU timing steps.

Fresh classification runs use learning rate `0.0001` and bound the VAE's log variance to `[-10, 10]` before both sampling and KL calculation. These settings address the large variance values observed on a few strong transients in the full five-second inputs; they do not clip or shorten the input WAV. The bounds are stored in the model configuration. Existing reconstruction/MSM checkpoints retain their original unbounded configuration unless it explicitly includes bounds. A full resume preserves its saved learning rate and variance configuration; start a new run to adopt the new defaults.

Training logs display the total loss, classification CE, reconstruction MSE, and KL separately. Gradient clipping retries a finite-gradient norm calculation in float64 if its float32 reduction overflows. Actual NaN/Inf gradients still stop training rather than being used for an optimizer update.

Every 20 epochs and at the final epoch, validation and test metrics are recorded. Only validation Macro F1 selects `best.pt`. Results go into `runs/train/<timestamp>/classification/cnn/` or `.../lstm/`. `last.pt` saves progress after each completed epoch, `final.pt` saves the final model, and `best.pt` saves the model selected on validation. `metrics.json` and `test_predictions.csv` report the selected model's evaluation and individual test labels/probabilities.

Classification reports display **ACC, P (macro), R (macro), and F1 (macro)**. ACC is the fraction of correctly classified samples. P and R first compute precision and recall for each configured class, then average classes equally; zero-denominator class values are 0. The JSON keys are `accuracy`, `macro_precision`, `macro_recall`, and `macro_f1`, stored on a 0–1 scale. Per-class precision/recall/F1 and the confusion matrix remain available. The same metrics are printed by the independent test command and saved in periodic history; unevaluated epochs have blank/null metric values. Resuming an older classification checkpoint fills missing P/R history from its saved confusion matrices.

Resume to a total of 300 epochs by replacing the checkpoint path with your actual run:

```bash
python main.py --mode train --task classification --model cnn --resume "runs/train/<timestamp>/classification/cnn/last.pt" --epochs 300
```

To run inference after training, choose a complete file or simulated streaming input:

```bash
python main.py --mode infer --input-mode file --model cnn --device auto --checkpoint "runs/train/<timestamp>/classification/cnn/best.pt" --wav "/path/to/recording.wav"
python main.py --mode infer --input-mode stream --model cnn --device auto --checkpoint "runs/train/<timestamp>/classification/cnn/best.pt" --wav "/path/to/recording.wav"
```

`--mode infer` defaults to `--task classification` and `--input-mode file`. File mode processes every complete five-second window without real-time waiting. Stream mode replays 20 ms chunks at recorded timing and predicts each time five seconds have accumulated; add `--no-realtime` for fast replay. Both modes accept longer WAVs, report incomplete tails without classifying them, and reuse the checkpoint's saved preprocessing and class mapping. Choose `--model lstm` with a matching LSTM checkpoint to use that model.

Device selection defaults to `--device auto`: a CUDA allocation, matrix calculation and synchronization must succeed before CUDA is selected; otherwise the program explains the reason and uses CPU. `--device cpu` forces CPU, and `--device cuda` requires the CUDA check to succeed. The selected device is shown in logs and recorded in JSON results. Existing saved weights are loaded on CPU first, then the model and input tensors are placed on the selected device. Errors after device selection, including an out-of-memory error during model execution, remain errors rather than silently restarting on CPU.

Classification inference saves `report.json` and `responses.jsonl` under `runs/inference/<Lisbon timestamp>/classification/<model>/<file|stream>/`. `--output-dir` changes the output root; each invocation gets a new timestamped directory. This reuses the local inference adapter in `Integration/simulate_monitor.py`; it does not start a gRPC server or calculate label-based test metrics.

The older `--mode predict --task classification` still accepts one complete five-second WAV, and `--mode stream --task classification` keeps its existing behavior and output paths. `--input-mode` is available only with `--mode infer`. For reconstruction checkpoints, explicitly select `--task reconstruction`; the new input choices route to the existing file/stream reconstruction workflows and retain their output formats. Old reconstruction/MSM checkpoints cannot be resumed as five-second classification models.

To use a separately retained matching dataset, pass its `samples.csv` with `--csv`. The selected CSV is read on each run and checked against the generation manifest. Keep all variants and segments from one original source in the same split. Because generation uses a training-only amplitude reference, changing source split membership requires rebuilding the dataset with the revised source assignments rather than moving generated rows between CSVs.

## Independent CSV export and inference verification

CSV generation for an existing dataset can now be run independently of WAV segmentation and sine injection:

```bash
python Dataset/Preprocessing/export_csv.py --data-dir Dataset/Processed_5s --output-dir "runs/csv_exports/<new-name>"
```

This exports `train.csv`, `val.csv`, `test.csv`, `excluded.csv`, and `samples.csv` into the new review directory. It preserves the existing source splits and manually edited split-CSV labels. WAV paths still refer to `Dataset/Processed_5s/`; the export directory is not a standalone dataset. The original WAVs and indexes are not changed. Without `--output-dir`, review exports go to `Dataset/CSV_exports/<timestamp>/`, outside the raw-data directory.

After training has completed, test the selected checkpoint on every held-out CSV row and verify that file and chunked inputs agree:

```bash
python Validation/verify_classification.py --model cnn --checkpoint "runs/train/<timestamp>/classification/cnn/best.pt" --output-dir "runs/verification/<new-name>/cnn_test"
```

Replay a longer WAV at its original timing through the same classification model:

```bash
python main.py --mode infer --input-mode stream --model cnn --checkpoint "runs/train/<timestamp>/classification/cnn/best.pt" --wav "Dataset/Data/20261012_124615/audio_000000.wav"
```

Add `--no-realtime` for a fast replay. CNN and LSTM use the same buffering contract: incoming chunks default to 20 ms, while a prediction needs a complete five-second window. Short tails are reported rather than inferred, and each new recording starts a new session. See [validation instructions](Validation/README.md) and the [gRPC interface study](Integration/README.md).

## Periodic evaluation and training checkpoints

Start a fresh 200-epoch reconstruction run with evaluation every 20 epochs:

```bash
python main.py --mode train --model cnn --epochs 200 --eval-every 20
python main.py --mode train --model lstm --epochs 200 --eval-every 20
```

`--epochs` is the total target epoch, including epochs already completed before a resume. `--eval-every` defaults to `20`. By default, each evaluation point runs both validation and test evaluation, and the final epoch is evaluated even if it is not a multiple of 20. Test results are logged for observation only; they do not choose `best.pt`, affect optimization, or control early stopping. The best checkpoint is selected from evaluated validation scores: lower reconstruction MSE for reconstruction, or higher interval-level Macro F1 for MSM.

Use `--no-test-during-training` if a future experiment should observe validation only during training; final test evaluation is still performed. The default remains periodic validation and test evaluation.

Each model's run directory contains:

| File | Purpose |
| --- | --- |
| `last.pt` | Resume state saved after every completed epoch |
| `checkpoints/epoch_0020.pt`, `epoch_0040.pt`, … | Snapshots at evaluation points |
| `best.pt` | Checkpoint selected using validation results |
| `final.pt` | Checkpoint at the end of the run |
| `smoke_trained.pt` | Reconstruction checkpoint retained for compatibility with existing prediction interfaces |
| `best_classifier.pt` | MSM classifier checkpoint retained for its existing inference interface |

To continue a saved run toward epoch 300, replace `<previous-timestamp>` with its actual directory name:

```bash
python main.py --mode train --model cnn --resume "runs/train/<previous-timestamp>/reconstruction/cnn/last.pt" --epochs 300
```

Use a matching task and model; `--resume` accepts one existing checkpoint file and is available only for single-model training. It cannot be combined with `--model both`, prediction, or streaming. The source checkpoint is retained, and continuation results are written under a new timestamp.

A full training checkpoint restores model weights, optimizer state, completed epoch, and Python, NumPy, CPU PyTorch, and data-loader generator RNG state. CUDA runs additionally save CUDA RNG state for matching-device continuation. Saved optimization and data settings are reused; extend the total epoch target or explicitly change the evaluation cadence as needed. An interrupted partial epoch is not preserved: resume from the last completed epoch saved in `last.pt`. Loading existing weights on a different supported device is allowed, but changing device or runtime does not promise bitwise-identical training or predictions.

Older checkpoints, including the existing 200-epoch `runs/reconstruction/cnn/smoke_trained.pt`, do not contain the complete optimizer/RNG training state. They support weights-only continuation with an optimizer reset, reported explicitly as such; this does not recreate the original training trajectory. These are training checkpoints, separate from gRPC or stream-connection recovery.

## Predict from a saved reconstruction checkpoint

Prediction loads the specified checkpoint and its saved normalization, then evaluates the WAV without retraining or refitting normalization. Select exactly one model, `cnn` or `lstm`; `both` is a training-only selection. Both `--checkpoint` and `--wav` are required.

The CNN example uses the saved 200-epoch reconstruction checkpoint:

```bash
python main.py --mode predict --model cnn --checkpoint runs/reconstruction/cnn/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav
```

The LSTM example uses its retained short-training checkpoint:

```bash
python main.py --mode predict --model lstm --checkpoint LSTM-VAE/artifacts/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav
```

For `main.py --mode predict`, `--max-windows` defaults to `0`, which processes all complete windows. A positive value limits processing to that many initial windows. Any incomplete final window is reported as trailing frames. For a bounded run with an explicit JSON destination:

```bash
python main.py --mode predict --model cnn --checkpoint runs/reconstruction/cnn/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav --max-windows 32 --output runs/prediction/cnn_first32.json
```

Without `--output`, prediction writes to `runs/prediction/<model>/<wav-parent-folder>/<wav-stem>_<checkpoint-stem>.json`. The first CNN example therefore writes `runs/prediction/cnn/20261012_124615/audio_000000_smoke_trained.json`. `--output-dir` changes the base directory while retaining the prediction/model/recording subdirectories. `--output` selects the exact JSON file.

The JSON records the absolute `checkpoint_file`, input WAV, processed-window count, trailing frames, per-window reconstruction errors, and latent features. Its `summary` contains the evaluated signal duration and mean standardized reconstruction MSE overall and for each channel. The console prints these summary values after inference. Evaluated duration describes the signal covered, not computation time. These are reconstruction-model outputs, not state-class labels or calibrated fault probabilities.

The examples in this section use `--task reconstruction`. For one five-second WAV and four class probabilities, use `--task classification` and its matching checkpoint as shown above. MSM classification requires separately aligned Sound0 PCM and Acc0 physical acceleration at 48 kHz; use the MSM `StateEngine` interface with its prepared two-modality inputs.

The original per-model prediction commands remain available. Their own default limit is 32 windows; pass `--max-windows 0` to request all complete windows directly:

```bash
python CNN1D-VAE/predict.py --checkpoint runs/reconstruction/cnn/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav --max-windows 0 --output runs/cnn_prediction.json
python LSTM-VAE/predict.py --checkpoint LSTM-VAE/artifacts/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav --max-windows 0 --output runs/lstm_prediction.json
```

Each model's supplied `artifacts/example_input.wav` also provides a small standalone input. Untrained checkpoints remain available for integration checks; select the intended checkpoint path explicitly.

Inputs are stereo PCM16 WAVs at 44.1 kHz. The saved reconstruction models use 2,048-sample windows, approximately 46.44 ms. The Python window interface can also return reconstructed waveforms; the WAV command-line output contains per-window errors and latent vectors.

`Dataset/Preprocessing/demo_windows.py` can generate one-second clips to illustrate segmentation and manual-label alignment. Use its `--output` option to choose a demonstration directory outside `Dataset/Data/`. This does not change the models' saved 2,048-sample input shape.

## Streaming replay

The unified streaming entry point replays an existing WAV at its recorded timing. Select exactly one model and provide its checkpoint and the input WAV:

```bash
python main.py --mode stream --model cnn --checkpoint runs/reconstruction/cnn/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav
python main.py --mode stream --model lstm --checkpoint LSTM-VAE/artifacts/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav
```

These examples use reconstruction checkpoints; replace historical paths with existing checkpoints from your runs. Classification streaming uses `--task classification` and its matching weights, as shown above. `main.py --mode stream` defaults to real-time pacing; add `--no-realtime` for fast replay. `--model both` remains training-only. Streaming replays the entire WAV and does not accept `--max-windows`.

`--chunk-ms` defaults to `20`: each input block contains 882 frames at 44.1 kHz. The checkpoint is loaded once, and its saved normalization is reused. `StreamingPredictor.push()` buffers incoming blocks and emits complete 2,048-frame windows, each covering approximately 46.44 ms. Each result is written and flushed to JSONL as it becomes available. The final incomplete window remains unprocessed and its frame count is recorded. The LSTM hidden state is reset for each window.

The console displays the first result, then the latest window's overall, L-channel, and R-channel standardized reconstruction MSE about once per second. At completion it reports the mean errors and processed signal duration. The separate JSON report records real replay time, residual frames, and timing measurements. These values describe reconstruction and runtime behavior; they are not class labels or calibrated fault probabilities.

Without explicit destinations, files are saved as:

```text
runs/stream/<model>/<wav-parent-folder>/<wav-stem>_<checkpoint-stem>.jsonl
runs/stream/<model>/<wav-parent-folder>/<wav-stem>_<checkpoint-stem>_report.json
```

For the CNN example, the JSONL is `runs/stream/cnn/20261012_124615/audio_000000_smoke_trained.jsonl`. Use `--output` for an exact JSONL path and `--report` for an exact summary path. Otherwise, the report is placed beside the JSONL and named `<output-stem>_report.json`. `--output-dir` changes the base directory while retaining the stream/model/recording structure.

An optional `--reference-json` compares streaming output with complete offline predictions from the **same WAV and checkpoint**. For the CNN commands above, first run the corresponding `--mode predict` command, then provide `--reference-json runs/prediction/cnn/20261012_124615/audio_000000_smoke_trained.json` to the streaming command. The offline reference must cover all complete windows, rather than a bounded prefix.

This mode simulates streamed input from a saved WAV. Live microphone capture and gRPC transport are separate integrations. Incoming data must satisfy the saved reconstruction model's 44.1 kHz, two-channel PCM contract.

The original standalone scripts remain compatible. Unlike the unified streaming mode, a direct script call requires explicit `--realtime` to replay at the WAV's timing; without it, the file is processed as quickly as possible:

```bash
python CNN1D-VAE/stream_wav.py --checkpoint runs/reconstruction/cnn/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav --realtime --output runs/cnn_stream.jsonl --report runs/cnn_stream_report.json
python LSTM-VAE/stream_wav.py --checkpoint LSTM-VAE/artifacts/smoke_trained.pt --wav Dataset/Data/20261012_124615/audio_000000.wav --realtime --output runs/lstm_stream.jsonl --report runs/lstm_stream_report.json
```

## Five-second sample preparation

The standalone entry exports nonoverlapping five-second stereo PCM16 WAV samples, creates the artificial class variants, and writes the combined CSV:

```bash
python Dataset/Preprocessing/prepare_dataset.py
```

The output is the fixed `Dataset/Processed_5s/` directory. Complete WAVs are organized as `<split>/<label>/<recording_id>/<segment>.wav`, with `samples.csv` and companion split CSVs at the dataset root. Original `good` WAVs preserve the base PCM values without resampling or normalization. The current 31 recordings produce 295 training, 35 validation and 39 test base samples, each containing 220,500 frames. All previously excluded recordings have been assigned to training at the user's request; validation and test assignments are unchanged.

Splits are assigned by original recording source before segmentation. The 12 training, 3 validation, and 3 test source groups do not overlap. Any later synthetic variants must inherit their base sample's source and split; do not randomly split variants or neighboring segments across sets. Fit normalization and amplitude-reference statistics on training data only.

The 27 incomplete tails are retained under `tails/` and in `tails.csv`/`tails.json`, with their actual lengths. They are not included in the three fixed-length sample CSVs, padded, or joined to another recording. Event annotations inherit the state at each segment's start; mixed-state spans and relative event times are retained. The two short tool-change recordings are preserved as tails.

`label=good` follows the professor's original-signal convention. Manual `machine_state` and `quality_score` remain separate fields; absent values remain empty/null. The root `segments.csv`/`segments.json` refer directly to the unchanged `good` WAVs, so the output does not store a second copy of all 369 base signals. `base_dataset_summary.json` records the base counts and tail summary.

The source assignments come from `Dataset/Preprocessing/dataset_splits.csv`. Preprocessing builds and validates temporary output before replacing `Dataset/Processed_5s/`. A failed build leaves the published dataset intact. Raw WAVs are not modified. Use `--dry-run` to preview inputs or `--verbose` for progress.

These five-second sample files are distinct from the model's internal windows. Existing reconstruction checkpoints still expect 2,048 points. Exporting the five-second dataset does not change that input shape or automatically start four-class training.

## Artificial four-class generation

`prepare_dataset.py` runs segmentation and synthesis together using `Dataset/Preprocessing/fourclass_config.json`. Its internal builders are `build_segments.py` and `build_fourclass.py`; they do not need separate commands in the normal workflow. Every complete base segment produces four actual five-second PCM16 stereo WAVs in `Dataset/Processed_5s/`: one original `good` version and three sine-injected versions. With the current 369 bases, this produces **1,476 WAV files**: 369 unchanged-good versions and 1,107 artificial variants. The 27 short tails remain separate and are not synthesized into classes.

| Artificial label | Added sine peak amplitude / training reference | Train | Validation | Test |
| --- | ---: | ---: | ---: | ---: |
| `good` | 0 | 295 | 35 | 39 |
| `sufficient` | 0.5 | 295 | 35 | 39 |
| `bad` | 1.5 | 295 | 35 | 39 |
| `very_bad` | 3.0 | 295 | 35 | 39 |
| Total | — | **1,180** | **140** | **156** |

These are **artificial amplitude-tier labels**, not measurements of real faults or machining-quality grades. The original `good` convention does not establish that a synthetic `bad` waveform represents an actual bad machining event. Manual event annotations are retained separately, including `original_quality_score`; a recorded numeric score of 3 is not converted into one of these four class IDs.

The current engineering defaults add a **1,000 Hz sine to the right channel only**. The sole amplitude reference is the median right-channel RMS of the **295 original training segments**, currently **290.2423828895374 PCM counts**. Validation and test segments, tails, and synthesized variants do not contribute to that reference. No conversion to a physical acceleration unit is implied.

For each base segment, one random phase and one amplitude multiplier in `[0.9, 1.1]` are shared by all four versions. Added peak amplitude equals `training_reference × class_ratio × shared_multiplier`; only the class ratio changes between the four versions. The configured seed is `20261109`. These frequency and amplitude settings are engineering defaults and have **not received the professor's exact confirmation**; the effective configuration and reference are recorded in `resolved_config.json`.

Every generated version inherits its base segment's `source_recording_id` and split. The four versions, neighboring segments, and clips from the same original acquisition must not be split again independently. The saved tables are a build-time snapshot:

- `samples.csv` and `samples.json`: all generated samples, their base/source provenance, artificial labels, and retained manual annotations.
- `train.csv`, `val.csv`, and `test.csv`: the corresponding sample memberships.
- `labels.json`: label definitions.
- `resolved_config.json`: the effective synthesis recipe and training-only reference.
- `dataset_summary.json`: generated dataset counts and summary.
- `segments.csv`, `segments.json`, and `base_dataset_summary.json`: original base references and counts.
- `tails/`, `tails.csv`, and `tails.json`: incomplete original tails and their annotations.

Synthesis parameters (amplitude, phase, and `label_index`), base/sample IDs, and filenames are label or provenance metadata, not classifier input features. The classifier should learn from the WAV signals; class labels serve as training targets.

Edit the recipe before preprocessing when changing the synthetic signal settings. Each successful preparation replaces the generated directory, including its CSVs and recipe snapshots. Retain a copy elsewhere when a previous experiment needs its exact data.

This step builds data only. Train on these existing WAV files explicitly with `main.py --task classification`, as described at the top of this README. Reconstruction and MSM training keep their respective data contracts.

## CSV-controlled training, validation, and test sets

Both models read the current CSV when a training run starts. Editing and saving the table changes the next run; a running experiment keeps the split it already loaded.

| Workflow | Shared CSV | Current assignments |
| --- | --- | --- |
| Company WAV reconstruction | `Dataset/Preprocessing/dataset_splits.csv` | 25 train, 3 val, 3 test, 0 exclude |
| MSM supervised classification | `Dataset/Preprocessing/msm_dataset_splits.csv` | 23 train, 7 val, 7 test |

Each CSV has these columns:

| Column | Meaning |
| --- | --- |
| `recording_id` | The sample folder name, or an MSM experiment ID such as `dataset1` |
| `source_recording_id` | The original acquisition from which the sample was extracted |
| `split` | Exactly `train`, `val`, `test`, or `exclude` |

Change the `split` column to move a recording between sets. Clips from one original acquisition must stay in the same active split. The reader reports duplicate entries, empty splits, invalid assignments, and source groups spread across different sets. Company loaders also check the source ID against each selected sample's metadata.

Every training run saves `dataset_splits_used.csv`, the resolved table actually used for that run. This records the experiment even if the editable input CSV changes later. Full checkpoint continuation preserves the saved data configuration and normalization rather than adopting a different split accidentally. Normalization continues to use training windows only; prediction reuses the normalization stored in its checkpoint.

## Company WAV reconstruction training

The unified commands above are the main training entry point. These original per-model commands remain compatible:

```bash
python CNN1D-VAE/run_demo.py --epochs 3
python LSTM-VAE/run_demo.py --epochs 3
```

The shared loader in `Dataset/Preprocessing/company_data.py` reads WAVs from `Dataset/Data/` and assignments from `Dataset/Preprocessing/dataset_splits.csv` by default. Both model directories import that same implementation. The current CSV uses all 31 source sample folders: 25 for training, 3 for validation, and 3 for testing. New clips from the same original recording are all kept in training. The generated `Dataset/Processed_5s/` directory is separate from these raw inputs. Direct trainer calls without an output override also use `runs/train/<timestamp>/reconstruction/<model>/`; an explicit trainer `--output-dir` must name a new or empty directory. Historical checkpoints retain their original saved split snapshots.

To resume a checkpoint trained on the earlier 16-recording split, pass that run's `dataset_splits_used.csv` explicitly with `--split-csv`. A full resume rejects a changed effective split rather than silently mixing the old training state with the new data allocation.

To use another split table, pass `--split-csv` to either model:

```bash
python CNN1D-VAE/run_demo.py --split-csv Dataset/Preprocessing/dataset_splits.csv
python LSTM-VAE/run_demo.py --split-csv Dataset/Preprocessing/dataset_splits.csv
```

The company CSV controls which WAVs enter reconstruction training; it does not convert the workflow into supervised event classification. Training on the company event labels still needs the corresponding labeled-window preparation. The 14 additional clips with event annotations all share one original recording. Their labels are not the MSM classification labels.

## MSM classifiers

Both directories include `classifier.py`, `state_runtime.py`, `train_msm.py`, and `artifacts/msm_classification/best_classifier.pt`.

The three MSM classes are `normal_cutting`, `abnormal_cutting`, and `defective_tool_normal_cutting`. These checkpoints expect aligned 48 kHz Sound0 PCM values and Acc0 acceleration in mm/s². They cannot directly treat the company's uncalibrated right-channel PCM values as acceleration.

MSM raw recordings and prepared arrays are external data dependencies. Provide their locations with `--raw` or `--prepared`; the shared training code and saved classifier weights are included here. See [the MSM workflow](msm_classification/README.md).
